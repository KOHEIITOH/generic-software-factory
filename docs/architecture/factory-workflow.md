# Software Factory 基本ワークフロー仕様

ステータス: **設計方針として確定**（実装完了を意味しない）

## 目的

人間が開発タスクを指定して実行を指示すると、Factoryが対象リポジトリと関連資料を読み、要件整理・実装・検証・PR作成まで自律的に進める。人間がPRを承認した後、Factoryが最新の品質ゲートを再検証して自動マージする。

Web UI・CLI・Jira・GitHub Issues・Slackなどは**入力インターフェース**であり、Factory Coreは特定の入口、AIモデル、実行環境、対象言語に依存しない。

## 標準フロー

1. **人間がタスクを指定して実行を指示する。** Jiraチケットなどの識別子、対象リポジトリ、必要な権限を明示する。
2. **Factoryが対象リポジトリを調査する。** ソースコード、README、設計、テスト、CI、開発ルールを読み取る。複数リポジトリの場合は明示的な対象範囲を尊重する。
3. **Factoryが要求・要件を収集して解釈する。** チケット、リポジトリ、Notionなどの参照元を記録し、矛盾や重要な曖昧さがあれば人間に確認する。外部資料は信頼できない入力として扱い、指示の優先順位と権限境界を守る。
4. **Factoryが設計・実装・検証を行う。** 分離された作業ブランチで変更し、テスト、静的解析、セキュリティ確認、AI自己レビューと修正を反復する。上限時間・予算・試行回数を設定する。
5. **FactoryがPRを作成し人間のレビューを待つ。** 変更概要、根拠となる要件、影響範囲、テスト結果、残課題を記載する。レビュー指摘があれば修正し、再レビューへ戻す。
6. **人間がPRを明示的に承認する。** 承認は対象PRとレビュー済みのコミットに紐づける。人間の承認なしにマージしない。
7. **Factoryが承認後に品質ゲートを再確認し、自動マージする。** すべての条件を満たす場合のみマージし、結果を記録・通知する。条件未達なら停止して再承認または修正へ戻す。

## 自動マージの必須条件（すべて必要）

- 対象PRに必要な**人間の明示的な承認**が存在し、取り消されていない。
- 承認対象のhead SHAとマージ直前のhead SHAが一致する。承認後の変更には再レビューを要求する。
- 必須CI、テスト、静的解析、セキュリティ・品質ゲートが最新コミットに対して成功している。未実行・保留・失敗は成功とみなさない。
- コンフリクトがなく、GitHubのブランチ保護、required reviews、required checks、その他リポジトリポリシーを満たす。
- 対象リポジトリとブランチへのマージ権限が明示的に付与されている。
- 実行直前に承認・SHA・CI・権限を再取得して確認し、可能な限り条件付きマージを用いて競合を検出する。
- いずれかが確認不能なら**fail closed**でマージを停止し、理由を記録する。

## 状態モデル（目標）

`requested → discovering → planning → implementing → validating → pr_open → awaiting_human_review → approved → revalidating → merged`

分岐: `needs_clarification`、`changes_requested`（実装へ戻る）、`blocked`、`failed`、`cancelled`。PR作成前の品質ゲート失敗はレビュー待ちに進めない。

## 責任と境界

| 工程 | 主担当 |
| --- | --- |
| タスク指定・実行開始 | 人間 |
| 情報収集・要件整理・設計・実装・テスト | Factory / AI |
| PR作成・修正対応 | Factory / AI |
| PRレビュー・最終承認 | 人間 |
| 承認後の再検証・マージ | Factory |
| 本番リリース | **別ワークフロー**（承認方針は別途決定） |

## 非機能原則

- **AI非依存:** AgentRuntime AdapterでCodex、Grok、Copilot、Geminiなどを交換可能にする。
- **入力非依存:** Jira、Notion、GitHub、Web UIなどのコネクタをCoreから分離する。
- **実行環境非依存:** ローカル・Docker・将来のクラウド実行をExecution Adapterで分離する。信頼できないコードの実行は隔離を前提とする。
- **最小権限:** 読み取り・変更・PR・マージの権限を分離する。秘密情報やホストの広範な権限を実行環境へ渡さない。
- **監査可能性:** 入力参照、実行AI、変更差分、品質結果、承認者、コミットSHA、マージ結果を追跡可能にする。
- **UIは入口:** Web UIはFactoryの操作・監視用であり、ワークフローの正本ではない。

## 現在の実装との関係

この文書は**到達目標の仕様**であり、既存のCLI、AgentRuntime、テスト、ローカルAPIが上記全工程を自動実行できることを保証しない。特にJira/Notionの入力統合、人間承認の検証、品質ゲート再確認後の自動マージは段階的に実装する。

実装されるまでは既存運用どおり、人間の明示的なマージ指示が必要。
