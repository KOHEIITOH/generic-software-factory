1. まず概要

一言でいうと、「AIに開発作業を頼むときの共通ルールと作業手順を定義する設計図」です。

特定のAI会社やプログラミング言語に固定されず、Planner（計画）、Developer（実装）、Tester（検証）、Reviewer（レビュー）などの役割を組み合わせて、依頼からPull Requestまでの流れを管理する構想です。

向いていること作業手順、責任分担、安全ルールを整理し、複数のAIツールやプロジェクトで共通化する。
これだけではできないことPython、uv、対応するAgent CLIのインストールと認証が必要です。業務コードへの安全な適用は未対応です。

2. 現在できること・できないこと

大切な前提: ローカルCLI、Task/Run/Audit管理、Codex/Grok/Copilot Adapter、Workflow・Policy・Quality Gate・改善ループの基礎を実装済みです。ただし任意リポジトリへの開発、PR自動作成、安全なOS隔離は未対応です。

今すぐできるのは、CLIによるTaskの作成・実行・結果参照、read-only接続確認、同梱サンプルへのCodexコード編集と単体テストです。Workflow実行と品質改善ループの基盤はPython APIとして存在しますが、CLIからの一気通貫実行は未実装です。GitHubリポジトリ連携やPR作成は今後実装予定です。

このガイドの位置づけ: 現状を実際以上に見せず、「構想の理解」と「導入・実装に向けた準備」に役立つようにまとめています。

3. 想定されている仕事の進み方

実装後は、おおむね次の順で作業を進める設計です。人の承認が必要な箇所を途中に設けます。

  1. 依頼を受け付け、設定を検証する
  2. Plannerが計画と完了条件をまとめる
  3. 人が計画を確認・承認する
  4. Developerが承認範囲を実装する
  5. Testerがテストや品質チェックを行う
  6. Reviewerが変更内容を独立して確認する
  7. Pull Requestを作成する
  8. 人が確認し、必要ならマージを承認する

チェックに失敗した場合や、要件が不明な場合は、無理に先へ進まず停止・質問する想定です。マージや本番デプロイをAIだけで完了させることは、現段階の目標ではありません。

6. 導入・実装に向けて準備すること

以下は試験運用や今後の拡張に向けて決めておく事項です。

  1. 対象プロジェクトを決める: 対象リポジトリ、主要言語、フレームワーク、既存の開発ルールを整理する。
  2. 作業範囲を決める: 最初は小さく、受け入れ条件を明確にできるタスクに絞る。
  3. 接続先を選ぶ: Agent Runtime、ソース管理、分離実行環境、必要であればモデルProviderを選ぶ。
  4. プロジェクト設定を用意する: test/lint/buildコマンドと完了条件を project.yaml にまとめる。
  5. Factory設定を用意する: Adapter、Workflow、承認条件、権限を factory.yaml にまとめる。
  6. 安全性を確認する: Secretの受け渡し、ネットワーク、隔離、権限、ログの扱いを決める。
  7. 人の承認点を決める: 計画、マージ、デプロイなど、誰が何を承認するか明確にする。

設定ファイルの例は 設定モデル、全体像は アーキテクチャ、実装の目標は MVP計画を参照してください。

7. 安全に使うための基本

  • AIに渡す依頼文やリポジトリの内容は、誤りや悪意ある指示を含みうるデータとして扱う。
  • AIに必要以上の権限や認証情報を渡さない。Secretを設定ファイル、prompt、ログに書かない。
  • 生成コードは隔離された環境で動かし、ネットワークやリソースを必要最小限に制限する。
  • テストやレビューを実行した証拠を残す。「Agentが大丈夫と言った」だけで合格にしない。
  • マージ、デプロイ、削除、権限変更は人の承認を必要とする。

詳細は セキュリティ基準と Safety Policyを確認してください。

8. 今後の改善候補

  1. Role参照の整合性: 不足している2つのHarness指示ファイルを追加するか、Role一覧との不一致を解消する。
  2. 動く最小構成: 既存CLIとWorkflow・Quality Gate基盤を安全なエンドツーエンド例として接続する。
  3. 初回セットアップ手順: 環境要件、設定方法、認証情報の登録、検証コマンド、想定結果を実装に合わせて記す。
  4. 承認と失敗時の運用: 誰が承認するか、失敗・中断・再試行時にどう復旧するかを具体化する。

この4点は、仕様書としての骨格を実際に試せる製品へ進めるための候補です。特にRole参照の整合性と、実行可能な縦切りのサンプルを優先すると利用者が試しやすくなります。
